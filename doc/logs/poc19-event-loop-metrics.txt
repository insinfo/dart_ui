FINDINGS  (polling 50ms = what poc_10 does today; oracle = what the proposed API would allow)
--------------------------------------------------------------------------------------------------------
1. A 60Hz frame timer runs at 16.0Hz under a 50ms polling loop, 59.2Hz under the oracle.
   Target 60.0Hz, pure-Dart baseline 61.0Hz. Frame gap p95 63.81ms -> 31.00ms.
2. Cross-isolate message latency p95 63.02ms -> 0.54ms (baseline 0.23ms). A wake handle removes the queueing delay entirely.
3. Idle wakeups/s 14.0 -> 0.3. Process cycles/s 12.7M -> 5.5M (baseline 2.6M).
   Caveat: the cycle counter is process-wide, so it also counts the sender isolate and the VM background threads.
   At this wakeup rate it cannot resolve the loop's own cost and the two numbers may even invert between runs.
   The defensible claim is the wakeup count itself, which is what keeps a core out of deep sleep states.
4. Spinning is not the escape hatch: 87% CPU animating, 116% idle, 3116M cycles/s while doing nothing.
5. The only available yield primitive, await Future.delayed(Duration.zero), costs 0.09ms p50 / 0.27ms p95 after a blocking wait,
   versus 0.00ms in a tight spin where the fast path is always hot. On a 16.67ms frame budget that is 0.5% spent re-entering the scheduler.
6. Isolate thread migrations across all runs: 0 (stable in this session, but nothing in the SDK promises it)
